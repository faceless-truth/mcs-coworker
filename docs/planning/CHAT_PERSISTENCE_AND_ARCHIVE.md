# Chat persistence and SharePoint archive

## 1. Overview

The Chat tab in MCS CoWorker now persists each specialist conversation
across tab switches and app restarts, and archives finished conversations
to the firm's SharePoint on demand via a "Finish chat" button. Phase A
(the schema plus persistence wiring) and Phase B (the archive pipeline
plus the button) ship together in v2.3 of the desktop app. The v3 rewrite
will revisit the persistence model end-to-end; this document reflects how
v2.3 is wired today.

## 2. Phase A — Session persistence

The schema contract is enforced in SQLite by a `UNIQUE (user_id,
specialist_key, status)` index on `chat_sessions`. That single constraint
is *the* guarantee that there is at most one active session per (user,
agent). Archived sessions don't compete because their status flips to
`'archived'` at finish-time, freeing a fresh `'active'` row to be created
on the next user message.

There is a deliberate naming asymmetry to be aware of: the API boundary
and Python helpers use **`agent_id`**, but the schema column is named
**`specialist_key`**. The column was named before the codebase settled on
`agent_id`; renaming would force a migration on every install for zero
functional gain. The mapping happens once, in the small handful of
helpers around `_resolve_chat_user_id` in `api_server.py` — not sprinkled
through call sites.

The frontend remains the source of truth for in-flight conversation
state. Backend persistence is a side-effect appended at the end of the
`/api/chat` handler (via `_persist_chat_turn`), not a reshaping of the
request. The backend never reloads prior turns to feed the Anthropic call
— the React client keeps full history in component state and includes it
in every request. Once we discovered the existing handler already
received that history per turn, we leaned into it rather than duplicating
the responsibility on the server.

## 3. Phase B — Finish chat → SharePoint archive

The finish endpoint orchestrates a fixed pipeline: title generation
(single-shot Haiku call in `generate_archive_title`) → in-memory `.docx`
build (`chat_export.build_chat_docx`, python-docx) → folder-exists check
on SharePoint → small-file PUT to the resolved folder → DB UPDATE setting
the session to `'archived'` with the SharePoint webUrl recorded. Every
step fails closed: any failure prior to the DB UPDATE leaves the session
`'active'` so the user can retry without losing the conversation.

The **explicit folder-exists GET before the PUT** is the mechanism behind
"do not auto-create folders." Graph's small-file PUT may auto-create
parent folders otherwise, which would silently create a phantom folder on
a folder-name typo. That is a governance bug, not a UX bug — fixing it
after the fact means hunting through SharePoint for files that ended up
in `MCS Coworkers/GST Speciallist/` instead of `GST Specialist/`.

| Tab in UI | `agent_id` | SharePoint subfolder |
|---|---|---|

| GST Specialist | `gst` | `GST Specialist/` |
| SMSF Specialist | `smsf` | `SMSF Specialist/` |
| Division 7A Specialist | `div7a` | `Division 7A Specialist/` |
| Trust Tax Specialist | `trusts` | `Trust Tax Specialist/` |
| Tax Structure Specialist | `tax_structure` | `Tax Structure Specialist/` |
| Individual Tax Deductions | `individual_tax` | `Individual Tax Deductions/` |
| Payroll Specialist | `payroll` | `Payroll Specialist/` |
| Net Wealth / SMSF Audit | `net_wealth` | `Net Wealth SMSF Audit/` |
| ATO Portal Assistant | `ato_portal` | `General/` |
| ATO Correspondence | `ato_correspondence` | `General/` |
| Plugin Builder | `plugin_builder` | — (excluded; see §6) |

Archive root within the SharePoint drive: `Server/Clients/MCS Coworkers/`.
The mapping lives in `graph_client.SPECIALIST_FOLDER_MAP`; display names
and short names are in `api_server.SPECIALIST_DISPLAY_NAMES` and
`SPECIALIST_SHORT_NAMES`. Adding a new specialist means three small map
edits, no other plumbing.

## 5. Filename format

`YYYY-MM-DD <Specialist Short Name> - <Auto-generated title>.docx`

The title is generated by a single Haiku call at finish-time
(`generate_archive_title` in `api_server.py`), then run through
`_sanitise_filename_part` for filesystem-safe characters. If the call
fails, returns empty, or the sanitiser strips it to nothing, the title
falls back to `<HH-MM> conversation` — a failed title call must never
block the archive itself.

## 6. Plugin Builder exclusion

Plugin Builder is excluded at three layers, by design:

- **Backend persistence**: `PERSISTED_AGENT_BLACKLIST` in `api_server.py`
  prevents `_persist_chat_turn` from writing rows for `plugin_builder`,
  preserving its original ephemeral behaviour.
- **Backend finish endpoint**: returns 400 with a clear message
  ("Plugin Builder sessions are not archived.") if `plugin_builder`
  reaches `/api/chat/<agent_id>/finish`.
- **Frontend button**: render-gated on
  `selectedAgentId !== "plugin_builder"` in `Chat.tsx`. The hardcoded
  string mirrors the backend constant — duplicated intentionally because
  the backend's Python set isn't reachable from TypeScript. If the
  blacklist ever expands, both layers must update.

The reasoning is that Plugin Builder sessions are tooling sessions, not
advisory work, and they should not end up in the firm's SharePoint as
artefacts.

## 7. Settings keys for SharePoint

| Setting key | Set how | Purpose |
|---|---|---|
| `sharepoint_site_id` | Auto-resolved by `get_sharepoint_site_id()` | Graph site identifier |
| `sharepoint_drive_id` | Auto-resolved by `get_sharepoint_drive_id()` | Graph drive (default Documents library) |
| `user_name` | Populated by `_populate_identity_settings` from `/me.displayName` | Used in the docx header |

Site and drive IDs are **not** cached to the settings table today — each
archive re-resolves them. This is a deliberate tradeoff: it costs one
extra Graph GET per archive (~200 ms) but means a tenant or library
rename does not leave a stale cached ID with no UI to clear it. Caching
is a future fix that should ship with a Settings UI override (see §9).

## 8. Known limitations

**Duplicate-upload race.** If the SharePoint PUT succeeds but the
subsequent DB UPDATE fails, a user retry produces a second copy in
SharePoint. The window is sub-second and the worst case is a duplicate
file an admin can delete. A three-state status machine
(`active` → `archiving` → `archived`) would prevent it but adds
complexity disproportionate to the risk.

**4 MB upload cap.** The Graph small-file PUT path used here works up to
~4 MB. Chat archives are well under this in practice. If they ever
exceed, upgrade to the upload-session endpoint (which `upload_to_sharepoint`
already uses for client-folder uploads).

**`_make_request` error specificity.** 404, other 4xx, and network errors
all collapse to `None` inside `_make_request`. So
`SharePointFolderMissing` is raised even when the real cause is a
permissions issue or a transient network blip. The user-visible error
message is the same ("folder not found"); the Graph audit log
distinguishes if needed.

**No SharePoint settings UI override.** If site/drive auto-resolve fails
(wrong tenant config, permissions, etc.), there is no in-app way to
override. Recovery today is via `test_sharepoint_connection()` or a
manual settings-table edit. A Settings UI override is a future fix.

**`window.open` external-link assumption.** The "Open" link on the
success toast uses `window.open(url, "_blank")`. WebView2 typically hands
these to the system browser, but pywebview environments vary. If smoke
testing reveals it does not open externally, the fix is a small backend
bridge endpoint calling `webbrowser.open()`.

**Welcome-message synthetic id.** The Finish button's "no real messages"
check filters on `m.id !== 0` — `0` is the synthetic id for the locally
rendered welcome message in `Chat.tsx`. Anyone changing the welcome
rendering must preserve this convention or the button will incorrectly
enable on fresh tabs.

**API response shape inconsistency.** `GET /api/chat/<agent_id>/active`
returns the codebase's standard `{ok, data}` envelope; `POST
/api/chat/<agent_id>/finish` returns a bare `{archived, web_url,
filename}` shape per the original task spec. Not worth fixing now (would
break A3's hydration logic); flag for a future API-consistency pass.

## 9. Future work (deferred, not abandoned)

**Site/drive caching with a Settings UI override.** Persist
`sharepoint_site_id` / `sharepoint_drive_id` after first successful
resolution and expose a Settings field to clear them. Saves the ~200 ms
GET per archive without trapping users on stale IDs.

**`webbrowser.open` backend bridge.** If pywebview turns out to swallow
`window.open(url, "_blank")` on any accountant's machine, add a tiny
`POST /api/open-external` endpoint calling `webbrowser.open(url)` and
have `Chat.tsx`'s "Open" toast action POST to it instead.

**"Show archived sessions" history panel.** Currently the archive lives
in SharePoint and is found via SharePoint, which is correct from a
governance standpoint but means there is no in-app rear-view of past
conversations. A read-only list within the Chat tab would speed up
finding a recent archive without leaving the app.

**Upload-session endpoint for archives over 4 MB.** Switch to the same
chunked upload path `upload_to_sharepoint` already uses for
client-folder uploads if archives ever start hitting the limit.
